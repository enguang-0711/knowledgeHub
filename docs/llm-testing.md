# 大模型辅助车载语音测试

LLM 最适合作为概率性助手处理语言、文档和文本归纳任务。测试系统仍要用版本化数据、明确 schema、确定性断言和可审计证据建立质量结论。

## 使用场景与控制方式

| 场景 | 模型输出 | 确定性/人工控制 |
|---|---|---|
| 需求转测试点 | 候选意图、边界、歧义与缺失信息 | 按需求逐条映射；由产品/测试审核覆盖率 |
| 同义表达扩充 | 候选语句和预计槽位 | schema 校验、语义校验、重复/泄漏检查、人工抽样 |
| 日志归因 | 可能组件、相关事件摘要 | 输出引用日志行/事件 id；工程师确认根因 |
| 失败聚类 | 相似错误组和趋势描述 | 由确定性特征计算，LLM 只给可读摘要 |
| 知识问答 | 基于检索片段回答 | 强制引用来源/版本；无证据时拒答 |
| 语义裁判 | 对自由表达给出语义相似判断 | 先用标注集校准精确率/召回率；关键路径独立断言 |

## 生成测试用例的流程

1. 只提供已批准的产品能力、意图/槽位 schema 和边界定义。
2. 要求模型按 JSON Schema 返回候选；不要解析随意 prose。
3. 验证必需字段、单位、槽位类型、合法值和目标标签。
4. 做重复检测、PII/敏感信息扫描、语义等价检查和风险分类。
5. 由人审核新意图、边界、危险命令和少数语言/方言内容。
6. 审核后的结果生成新的语料版本，不直接覆盖黄金集。
7. 在冻结的审查集上评估模型提案的有效率、重复率、语义错误率和人工审阅成本。

## LLM 作为裁判

对“表达是否大致等价”可以试用语义裁判，但输出需要校准。准备由专家标注的正负对照集，尤其包含否定、数值、单位、方向、时间、音区和槽位冲突；按类别测 precision/recall 和一致性。对错误代价高的关键槽位采用确定性比较或双重审查。所有裁判结果至少保留模型、提示、输入和原始响应，版本更新需重新回归。

提示中要避免泄漏 gold label 给裁判；从测试输入、模型输出和上下文构造对抗样例，检查裁判是否受措辞、顺序、系统提示注入或输出长度影响。对比“规则/专家/模型”分歧并记录仲裁结果。

## RAG 知识库问答

将内部规范按版本和权限切分为带 metadata 的片段；检索结果提供源文件、章节、版本、生效时间和授权标签。回答必须绑定检索证据，过期版本、冲突版本和无结果要显式处理。定期用标准问题集检查召回率、引用正确率、答案支持率、拒答质量和权限隔离；不要把 Markdown Pages 搜索等同于经过治理的企业 RAG 系统。

## 数据安全和模型治理

- 明确模型部署位置、数据是否留存/用于训练、访问控制、数据跨境和客户合同限制。
- 默认使用合成或脱敏内容；客户语音、车架/用户身份、内部日志和密钥只有在明确授权且符合政策时才能发送。
- 记录模型名称/版本、API 参数、prompt 版本、检索 corpus 版本、输入摘要和响应。
- 对模型输出做格式/长度/资源限制；将内容视为不可信数据，不能当 shell/车控命令执行。
- 质量门槛变更、自动修复测试和自动发送设备操作都需要额外控制与审计。

## 适合落地的渐进顺序

先在离线、低风险的数据整理和报告摘要上试用；测量节省的人工时间及审查错误。再用于候选用例扩充和失败聚类。最后才评估受控语义判定。每一步都设置关闭开关、人工回退和版本回滚。
