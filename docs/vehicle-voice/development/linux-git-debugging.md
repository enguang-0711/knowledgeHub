# Linux、Git 与音频调试

语音算法开发经常跨越 Linux 主机、车机、DSP/加速器和测试台架。能够快速确定进程、设备、库、线程和音频流状态，是定位问题的基础。

## Linux 与设备基础

掌握进程/线程、权限、信号、环境变量、动态库、文件描述符、网络接口和设备节点。检查音频设备实际采样率、声道数、缓冲块大小、时钟和播放/采集方向。服务启动环境可能与交互 shell 不同，应记录环境变量和动态库版本。

## Git 与模型制品

代码使用聚焦提交、审查和标签；模型/语料等大文件不应无来源地复制进仓库。保存制品版本、哈希、来源、许可和转换配置。一次可复现报告要能指向代码 commit、模型、词典、语料和运行参数。

## 调试路径

1. 检查设备和服务是否在线，采集是否持续，帧数/时间戳是否变化。
2. 查看波形峰值、RMS、静音、削波和通道，确认输入真实到达预期模块。
3. 检查线程栈、锁等待、队列深度、欠载/溢出计数和延迟。
4. 查看 ASR/NLU/TTS 事件、错误码和会话关联 ID。
5. 用 profiler 定位 CPU/DSP/加速器/数据搬运瓶颈。

GDB、sanitizer、系统日志、音频路由诊断和平台 profiler 解决不同问题。保存原始日志并标注设备/固件版本；包含录音或个人信息的日志按项目隐私策略处理。

## 常见问题

- 服务和交互 shell 使用不同设备或库版本。
- 只看音频文件存在，不验证采集回调实际收到非零样本。
- 播放设备有声音，但采集通道静音或路由到了另一个麦克风。
- 仅凭 ASR 最终文本定位错误，忽略上游音频已经削波或断续。

## 练习与完成标准

构造采集断流、播放设备切换和队列过载三个故障；通过日志、线程和波形证据分别定位。修复后记录复现命令、版本和对照指标，并用 Git 提交可审查的变更。
