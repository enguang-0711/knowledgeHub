# 语音需求与系统架构

车载语音开发应从用户任务和系统边界开始。一个可运行的 ASR 模型只覆盖语音链路的一部分；唤醒、音频前端、语义、业务调用、车辆状态和反馈都可能影响完整功能。

## 将需求写成接口契约

明确任务类型、允许表达、支持语言、期望输入方式、目标延迟和输出状态。每个意图定义必需槽位、类型、单位、范围、枚举、默认值、澄清/拒识规则和执行权限。系统应能表达识别中、完成、取消、超时、失败、无效输入和服务不可用等状态。

语音输出契约可包含 partial/final 文本、词/句时间戳、置信度、语言、拒识标志和会话 ID；业务接口要定义结构化动作和幂等/重试行为；车辆状态要有确认信号和更新时间。每个字段都要说明生产者、消费者和失效语义。

## 链路与时序

```text
麦克风 → 驱动/缓冲 → AEC/NS/AGC/波束形成 → 唤醒/VAD/端点
→ 流式 ASR → NLU/槽位 → 对话管理 → 业务服务/车辆接口
→ TTS/HMI → 播放结束/会话关闭
```

实际系统可能并行、分进程或依赖云服务。图中标出运行设备、通信协议、时钟来源、缓冲队列和断网行为。将端到端时限分配到前端、识别、语义、业务和播报；对超时后的补偿、取消和迟到事件定义规则。

## 架构设计关注点

- **实时音频：**采集与处理回调、缓冲深度、线程优先级、丢帧策略。
- **服务边界：**流式音频输入、异步事件、会话管理、错误码和服务版本。
- **状态管理：**会话、音区、用户、上下文、打断和重置。
- **离线/在线：**本地与云端能力、网络切换、隐私策略和降级行为。
- **资源限制：**模型内存、CPU/加速器、温度、启动时间和并发会话数。

## 常见架构误区

- 将“ASR 返回了文字”当作用户任务完成。
- 只定义正常输出，没有错误码、过期结果、取消或重启行为。
- 把播放器成功当作音频已到达指定麦克风/音区。
- partial 文本直接触发不可逆动作，没有 final 确认或策略限制。
- 识别结果、车辆状态和播报没有统一会话/请求 ID，无法还原时序。

## 练习与完成标准

选择一个低风险语音功能，画出组件图和时序图，定义输入输出 schema、超时、取消、重试和失败状态。为每个阶段写一个正向和异常事件；另一位开发者应能依据契约实现 mock 服务并复现主流程。
