# 对话管理与上下文状态

对话管理器根据当前意图、槽位、会话历史、权限和业务状态决定下一步动作：执行、询问缺失信息、澄清歧义、确认、拒绝或结束会话。

## 状态建模

一个会话至少需要明确 session/user/zone 标识、当前任务、槽位状态、待确认动作、超时和生命周期。状态机描述事件触发的迁移；测试侧预期状态与产品实现应独立，不能让同一状态判断代码既执行又判定自身正确。

任务型对话常见迁移包括开始、补槽、确认、执行、失败、取消、超时和重试。每个迁移应考虑幂等性、重复事件和迟到响应。

## 上下文策略

“再高一点”“换到后排”依赖上下文指代。系统应限定可引用的最近对象和有效时间；新任务、音区切换、用户切换或重启时如何清理上下文由产品策略定义。未确定引用时应澄清而非猜测。

## 生成式与规则式策略

可以使用规则、分类策略、对话状态机或生成式模型。涉及车辆动作时，生成内容应映射到受约束的动作 schema，并经过权限、类型和范围校验；不能把自由生成文本直接当作控制命令。提示词/模型版本和回退行为需可追踪。

## 失败和恢复

定义 ASR 无结果、NLU 低置信度、必需槽缺失、业务服务超时、状态与请求冲突、TTS 失败和用户取消时的反馈。执行已经发生但确认消息丢失时，应查询业务状态或使用请求 ID 去重，避免盲目重复执行。

## 练习与完成标准

实现包含补槽、改口、取消、超时和会话重置的状态机；为每轮记录输入、当前状态、槽位、动作和响应。注入重复与乱序事件，验证不会执行旧参数或将会话上下文泄漏到其他音区。
