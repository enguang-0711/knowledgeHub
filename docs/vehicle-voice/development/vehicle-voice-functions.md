# 车载语音业务与车辆接口

语音系统不应把原始文本直接转换成任意车辆控制。正确的开发路径是先将表达解析为类型化意图和槽位，再执行权限、状态和参数校验，最后调用受控业务服务。

## 命令到业务动作

```text
语音文本 → 意图/槽位 → 规范化参数 → 权限/范围/状态检查
→ 业务服务请求 → ECU/应用执行 → 状态回读 → TTS/HMI 反馈
```

每一阶段独立记录请求 ID、结果码和时间戳。槽位需要校验范围、单位、枚举和当前车辆配置；含糊或非法值应澄清/拒绝。需要确认的动作应由策略层确定，不由 ASR 置信度单独决定。

## 车端接口

根据平台选择应用服务、车辆服务 API、总线或中间件。接口定义包含命令与状态反馈的区别、单位/缩放、有效位、超时、更新频率、版本和权限。CAN/以太网协议的写操作只能按项目授权在隔离台架执行；开发练习使用 mock 或仿真接口。

“命令已发送”“服务接受”“车辆状态已改变”“用户得到正确反馈”是不同的里程碑。最终结果应通过独立状态查询或事件确认，避免仅凭成功播报判断执行完成。

## 幂等、权限和失败

重复请求需定义幂等键或去重窗口。服务超时不代表命令未执行；重试前应查询状态或使用请求 ID。用户/音区权限、驾驶状态和系统故障可能限制功能，需要进入明确拒绝或降级流程。

## 练习与完成标准

构建一个 mock 空调或媒体服务：输入结构化意图，校验参数，改变模拟状态并返回事件。测试非法温度、未知媒体、重复请求、超时、状态反馈不一致和拒绝执行。日志应能串联语音请求与最终状态。
