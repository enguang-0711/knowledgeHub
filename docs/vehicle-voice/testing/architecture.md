# 端到端系统架构与测试边界

## 一次语音请求经过哪些环节

典型链路可以抽象为：

```text
语料/实时说话
  → 声源与座舱声学路径
  → 麦克风/音区/音频前端（AEC、NS、AGC、波束形成）
  → 唤醒与端点检测
  → ASR（流式/最终文本）
  → NLU（意图、槽位、置信度）
  → 对话管理（上下文、澄清、权限和策略）
  → 业务服务/车控网关/媒体服务
  → 车辆信号或应用状态
  → TTS 与 HMI 反馈
```

量产实现可能把组件合并、并行或外包给云端；测试图应按实际架构更新。不要把“播报正确”当作“业务执行正确”，也不要把一条 NLU 日志当作车端动作成功。

**本知识点学习卡**

- **先修：**音频采样、客户端/服务端基本概念。
- **重难点：**组件可能串行、并行或跨进程；要区分内部阶段成功与用户可见/车辆状态真正成功。每个边界都应有事件和时间戳。

## 被测对象与测试台架

| 层 | 被测能力 | 典型输入 | 主要证据 | 常见误判 |
|---|---|---|---|---|
| 声学/前端 | 收音、音区、AEC/NS/AGC | WAV 经扬声器播放或真实说话 | 参考麦克风/回采、声压和通道配置 | 文件直接注入 DSP 被误认为覆盖真实麦克风链路 |
| 唤醒/VAD | 唤醒、端点和打断 | 唤醒词、近似词、噪声 | wake event、时间戳、误唤醒窗口 | 只统计成功次数，不记录无语音暴露时间 |
| ASR | 语音到文本 | 音频、语言/热词设置 | partial/final transcript、置信度、时延 | 参考文本归一规则不同，WER 不可比较 |
| NLU/对话 | 语义理解和多轮状态 | 文本或流式识别事件、会话历史 | intent/slots、会话 trace、状态事件 | 单轮用例通过掩盖状态残留/跨音区串话 |
| 业务执行 | 服务调用和状态改变 | 结构化意图或对话动作 | API/服务事件、车辆信号、应用状态 | 播报“已打开”但信号未改变 |
| HMI/TTS | 可理解反馈和屏幕状态 | 执行结果、提示策略 | 播报事件/音频、屏幕控件/文字 | OCR 动态文本或动画引入误判 |
| 系统工程 | 性能、稳定性、CI | 版本化套件和环境 | 端到端时间线、资源和构建元数据 | 重试掩盖间歇性故障、失败无工件 |

**本知识点学习卡**

- **先修：**系统边界、输入输出、观测点。
- **重难点：**文件注入、软件注入和声学播放覆盖的路径不同；报告必须标出注入点及绕过的组件。

## 建议的执行适配器

用接口隔离车厂私有工具和真实设备：

- `AudioInjector`: 选择音区/通道、播放、标记时间、设置已校准增益。
- `VoiceEventSource`: 订阅唤醒、ASR、NLU、会话和业务事件。
- `VehicleAdapter`: 查询或订阅允许的车辆/模拟器状态；不要将未经批准的写控制封装成通用默认方法。
- `HMIObserver`: 查询可访问性树、应用状态或截图/OCR。
- `EvidenceStore`: 保存结构化事件和原始日志、音频、截图、总线 trace。
- `Clock`: 提供统一时间戳或记录来源时钟和同步偏差。

同一组测试可以在 mock、模拟器、台架和 HIL 上复用测试描述；适配器应显式声明每个环境覆盖了哪些系统路径。

**本知识点学习卡**

- **先修：**Python 类、接口、依赖注入。
- **重难点：**接口要暴露环境能力和限制；不要让 mock 的通过结果伪装成真实麦克风或车辆总线覆盖。

## 闭环的最小判定

一条“打开空调”的用例可以分别判断：

1. 唤醒事件是否在时限内发生。
2. 最终 ASR 文本是否落入预设等价/严格匹配策略。
3. 意图和目标槽位是否正确。
4. 对话管理是否通过策略检查并发出业务请求。
5. 车辆/仿真状态是否达到目标值，并保持规定观察窗口。
6. HMI/TTS 是否按产品规范反馈。
7. 全链路时延是否满足项目门槛，且起止时刻来自明确定义的事件。

把这些断言分别记录，报告才有诊断价值。若某层的内部接口不可用，使用下游独立证据并标注覆盖盲区。

**本知识点学习卡**

- **先修：**事件驱动测试、断言与证据独立性。
- **重难点：**播报“成功”、业务请求被接受和车辆状态落地是三件事；用不同证据分别断言。

## 多轮和多音区建模

为会话定义明确状态：`session_id`、`zone_id`、历史轮次、当前意图、槽位、待澄清槽和超时。测试序列应覆盖正常补槽、改口、否定、取消、打断、重复请求、等待超时、会话重置及同一时段不同音区输入。每个轮次使用 trace id 关联事件，校验上一个会话的上下文不会污染新会话。

**本知识点学习卡**

- **先修：**状态机、会话和事件时序。
- **重难点：**上下文残留、并发和音区串扰往往是时序问题；测试数据必须包含会话 ID、音区 ID 和逐轮预期。

## 设计时的关键问题

- 输入在哪里注入？是否经过麦克风、AFE、AEC 和唤醒链路？
- 是否能区分“没有事件”和“采集/订阅器掉线”？
- 结果证据是否独立于同一套内部日志？能否用车辆状态或第二观测面交叉验证？
- 时钟是否同步？如果不同步，最大偏差是多少？
- 测试执行完怎样恢复到已知初始状态？恢复失败算什么类别？
- 每个动作是否安全、授权、可逆？有哪些硬件联锁或人工中止方式？

**本知识点学习卡**

- **先修：**需求拆解和可观测性。
- **重难点：**任何断言都要能区分产品失败、采集器失效和证据缺失；时间戳需标出时钟来源与误差。
