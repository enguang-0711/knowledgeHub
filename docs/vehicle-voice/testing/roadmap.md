# 车载语音自动化测试专题学习路线

这是一条建立在通用测试与质量工程能力之上的行业专题路线，按“能解释系统 → 能离线度量 → 能稳定注入 → 能证明业务结果 → 能规模化回归 → 能负责任地应用 AI”推进。日历只是建议；每阶段以产物和验收结果为准。若尚不熟悉测试设计、Python 或 CI，可先走[通用学习路线](/roadmap)。若已有 Python、车机或声学经验，可缩短相应阶段，但不要跳过指标口径和可复现性。

## 总体节奏

以每周 8–12 小时为例，建议 20 周完成一个可演示的端到端能力。企业项目的设备、算法接口和台架可用性会影响实际时间。

| 阶段 | 周数 | 主题 | 必交付物 | 进入下一阶段的门槛 |
|---|---:|---|---|---|
| 0 | 1 | 需求拆解与实验纪律 | 系统边界图、风险清单、开发环境 | 每个预期结果都有可观测证据 |
| 1 | 2–4 | Python 测试工程与 Git | Python 包、pytest 用例、结构化报告 | 在本地一条命令跑完且失败可定位 |
| 2 | 5–7 | 音频、声学与语料 | 版本化语料集、音频校验器、噪声实验 | 输入文件和声学条件可复现 |
| 3 | 8–10 | ASR/NLU/对话评估 | WER/CER、意图槽位和多轮评测报告 | 能区分算法错误、数据错误和评测错误 |
| 4 | 11–14 | 车机接入与闭环断言 | ADB/设备适配器、日志/UI/总线断言 | 业务状态可由独立信号证明 |
| 5 | 15–17 | HIL、CI 与趋势 | 可自动执行的冒烟/回归流水线 | 报告含版本、环境、证据和趋势 |
| 6 | 18–20 | 大模型辅助与质量治理 | AI 用例草稿、受控裁判评测、治理说明 | AI 输出可审查；关键通过/失败不依赖自由生成结论 |

## 阶段 0：需求、边界和实验纪律（第 1 周）

### 学习内容

- 把需求拆成触发条件、输入、前置状态、动作、可观测结果和失败恢复。
- 区分系统被测对象（SUT）、测试台架、音频播放设备、采集设备、仿真服务和判定器。
- 为每个断言指定“证据源”：ASR/NLU 日志、应用状态、HMI 文本、CAN/Ethernet 信号或人工复核。
- 确认车端动作的安全级别。涉及车辆运动、门锁、车窗、空调等功能时，在隔离台架或授权环境验证，并设置硬件/软件安全联锁。
- 学习缺陷复现的最小条件：SUT 版本、标定/模型版本、语料版本、播放/录制链路、环境和时间戳。

### 动手任务

选一个低风险、可观测的指令（例如查询空调状态或媒体状态），画出“说话到结果”的信号链。列出每个阶段成功和失败的外部证据，指出最可能出现的混淆因素。

### 通过标准

交付一页系统边界图和一张风险表；任何“成功”都能指出具体证据，不能只依赖测试脚本返回 0 或语音播报听起来正确。

**本阶段学习卡片**

- **先修：**需求阅读、软件测试用例和基本系统边界概念。
- **重难点：**把“听起来正常”改写成可观测的阶段结果；区分被测对象、测试设备和判定器，并为车端动作设置安全边界。
- **学习文档：**[端到端架构](/vehicle-voice/testing/architecture)、[多模态断言](/vehicle-voice/testing/multimodal-assertions)、[术语词典](/glossary)。
- **B 站学习入口：**[软件测试需求分析与测试用例设计](https://search.bilibili.com/all?keyword=%E8%BD%AF%E4%BB%B6%E6%B5%8B%E8%AF%95%E9%9C%80%E6%B1%82%E5%88%86%E6%9E%90%E4%B8%8E%E6%B5%8B%E8%AF%95%E7%94%A8%E4%BE%8B%E8%AE%BE%E8%AE%A1)。

## 阶段 1：Python 与测试工程（第 2–4 周）

### 必会细节

- Python：类型注解、dataclass、异常边界、pathlib、logging、JSON/YAML、虚拟环境、依赖锁定、包与模块。
- 测试结构：Arrange/Act/Assert、fixture 生命周期、参数化、标记、重试的适用边界、临时目录、清理和超时。
- 数据驱动：用例数据与执行逻辑分离；输入、前置条件、期望结果、采集证据和环境标签结构化存储。
- 报告：每次运行保留唯一 run id、提交 SHA、SUT/模型版本、执行设备、时区统一后的时间戳、原始证据位置。
- 失败语义：区分测试失败、环境失败、基础设施失败、测试数据无效、判定器异常和不确定结果。
- 代码质量：格式化、lint、类型检查、可复现依赖安装和 Git 分支/评审流程。

### 建议练习

构造一个不连接真车的 `VoiceSystemAdapter` 假实现，编写“调用命令→等待事件→检查业务状态”的 pytest。故意制造超时、设备离线、日志缺失和期望不匹配，验证报告是否清楚。

### 通过标准

克隆干净目录后能按 README 安装并执行；一次失败能从报告定位用例、阶段、输入与证据。

**本阶段学习卡片**

- **先修：**基础编程、命令行和 Git 基本操作。
- **重难点：**fixture 生命周期、异常边界、异步等待、资源清理和失败分类；不要用固定 sleep 或无边界重试掩盖时序/产品问题。
- **学习文档：**[Python/pytest/Robot Framework](/automation-framework)、[pytest 官方文档](https://docs.pytest.org/en/stable/)、[Robot Framework 用户指南](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html)。
- **B 站学习入口：**[Python pytest 自动化测试 fixture 参数化](https://search.bilibili.com/all?keyword=Python%20pytest%E8%87%AA%E5%8A%A8%E5%8C%96%E6%B5%8B%E8%AF%95fixture%E5%8F%82%E6%95%B0%E5%8C%96)。

## 阶段 2：音频、声学和语料（第 5–7 周）

### 必会细节

- 数字音频：采样率、位深、声道、PCM/容器格式、端序、峰值和 RMS、削波、静音、重采样与混叠。
- 声学链路：文件播放器、功放/扬声器、人工嘴或声学播放设备、座舱/台架、麦克风阵列、AEC/降噪/AGC、DSP 和录音回采。
- 测量与校准：播放器增益、麦克风位置、声压级、频响、设备延迟、左右/多音区位置、重复性和校准记录。
- 噪声：风噪、路噪、空调、音乐、乘员对话、瞬态噪声；噪声底、SNR、频带与时间变化；不同场景不应只由单个 SNR 值概括。
- 语料元数据：原始文本、规范化文本、说话人授权/来源、语言和口音、合成器/音色/参数、音频校验和、格式、声学条件、预期转写、标签、用途和许可。
- 合成语音局限：TTS 有利于批量、可重复覆盖，但音色、韵律、发音错误和声学分布可能与真人不一致；保留真人代表性语料及隐私授权流程。

### 建议练习

构建 50 条覆盖数字、单位、地名、品牌词、同音词和口语表达的小型数据集；为每条生成至少两种合成语音；制作干净、音乐、空调三种条件；用脚本校验时长、采样率、声道、静音、削波和文件哈希。

### 通过标准

别人拿到语料清单和版本标识后，能找到完全相同的源音频与派生音频，并知道每个派生文件采用的参数。

**本阶段学习卡片**

- **先修：**文件/目录、二进制数据和基本分贝概念。
- **重难点：**采样率/位深/声道必须与实际内容一致；数字混音噪声与声学播放噪声覆盖不同；TTS 母版和派生音频要有参数及哈希血缘。
- **学习文档：**[音频与声学](/vehicle-voice/testing/audio-acoustics)、[语料与 TTS](/vehicle-voice/testing/corpus-tts)、[术语词典](/glossary)。
- **B 站学习入口：**[数字音频基础 采样率 位深 TTS 声学测试](https://search.bilibili.com/all?keyword=%E6%95%B0%E5%AD%97%E9%9F%B3%E9%A2%91%E5%9F%BA%E7%A1%80%E9%87%87%E6%A0%B7%E7%8E%87%E4%BD%8D%E6%B7%B1TTS%E5%A3%B0%E5%AD%A6%E6%B5%8B%E8%AF%95)。

## 阶段 3：ASR、NLU 和对话评估（第 8–10 周）

### 必会细节

- ASR：参考文本规范化、分词边界、标点/大小写策略、热词、流式 partial 与 final、端点检测、时间戳、置信度、拒识和空结果。
- WER/CER：明确文本归一规则和评测单位；保存替换、删除、插入明细；不要只看总分，按意图、词类、噪声、口音、音区、设备和版本分层。
- 语义：意图准确率、宏/微平均、混淆矩阵；槽位精确率/召回率/F1、必填槽完整率、值归一化和错误严重度。
- 对话：上下文变量、轮次关联、打断/取消、澄清、拒识、超时、并发、会话重置、跨音区隔离、状态残留。
- 评测有效性：冻结测试集、数据泄漏检查、难例分层、基线版本、置信区间/样本量意识、人工抽检和判定器校准。
- 流式与时延：区分首字/首事件时延、最终识别时延、NLU 时延、业务执行时延和端到端时延；使用同一时钟域或明确时钟同步误差。

### 通过标准

生成一份可重复的离线评测报告，既能展示总体指标，也能追溯单条错词、意图/槽位错误和对应音频条件。

**本阶段学习卡片**

- **先修：**阶段 2 的音频和语料资产，以及分类指标基础。
- **重难点：**评测器不能把规范化差异误当语义正确；拆分 ASR、NLU、对话状态和业务错误；小样本分数要报告样本量和不确定性。
- **学习文档：**[ASR/NLU/对话评测](/vehicle-voice/testing/asr-nlu-dialogue)、[质量指标](/vehicle-voice/testing/metrics)、[术语词典](/glossary)。
- **B 站学习入口：**[WER CER ASR 评测 意图识别槽位抽取](https://search.bilibili.com/all?keyword=WER%20CER%20ASR%E8%AF%84%E6%B5%8B%E6%84%8F%E5%9B%BE%E8%AF%86%E5%88%AB%E6%A7%BD%E4%BD%8D%E6%8A%BD%E5%8F%96)。

## 阶段 4：车机接入与多模态断言（第 11–14 周）

### 必会细节

- Android/车机：ADB 设备选择、授权/连接状态、包信息、logcat 过滤、时间戳、崩溃/ANR、权限和设备清理；刷机、回滚、数据擦除要有显式前置检查。
- 音频注入：优先经过真实麦克风声学路径；记录播放起止标记、增益、位置、通道和录音回采。软件注入可用于特定层验证，但要标注其绕过的硬件/算法路径。
- 日志：从无结构文本提取稳定事件；优先使用结构化事件 ID、trace/session ID、组件时间戳和版本字段；避免仅凭易变文案断言。
- UI：页面/控件状态优先于像素截图；OCR 需要置信度、区域、语言和多帧稳定策略；截图差异需控制分辨率、缩放、主题、动画和动态区域。
- CAN：信号缩放、偏移、单位、枚举、周期、超时和有效位；DBC 版本、总线通道、节点、时间戳、信号更新窗口及发送/接收方向。
- Ethernet/服务接口：服务/事件/方法、端点、超时、版本兼容、网络隔离、诊断/追踪接口；DoIP、SOME/IP 等按项目协议栈和授权工具学习。
- 关联证据：用 run id/session id 和统一时基把语音输入、识别事件、业务调用、UI 变化和信号变化串起来。

### 通过标准

一条车端用例失败时，报告能区分“没唤醒、识别错误、语义错误、执行未发生、信号/界面不一致、证据缺失、环境失效”。

**本阶段学习卡片**

- **先修：**阶段 1 的设备适配器和阶段 3 的事件/状态评估。
- **重难点：**明确软件注入绕过的硬件路径；状态信号要校验解码版本、有效位和稳定窗口；多个屏/总线/日志时间需要关联。
- **学习文档：**[车机与总线](/vehicle-voice/testing/vehicle-integration)、[多模态断言](/vehicle-voice/testing/multimodal-assertions)。
- **B 站学习入口：**[ADB CAN DBC HIL 车载自动化测试](https://search.bilibili.com/all?keyword=ADB%20CAN%20DBC%20HIL%20%E8%BD%A6%E8%BD%BD%E8%87%AA%E5%8A%A8%E5%8C%96%E6%B5%8B%E8%AF%95)。

## 阶段 5：HIL、CI 和持续质量（第 15–17 周）

### 必会细节

- HIL 资源：台架占用/预约、设备健康检查、通道映射、网络隔离、校准状态、恢复到已知状态和紧急停止。
- 测试分层：静态检查/单元、离线 ASR/NLU、模拟集成、单台设备冒烟、完整 HIL 回归；慢且昂贵的套件按风险触发。
- CI：构建触发、固件/应用/模型制品、测试数据版本、环境资源锁、超时、取消、重试策略、并发与隔离、失败时保留日志/音频/截图/总线记录。
- 报告与趋势：版本维度、场景维度、设备维度、置信区间和样本量；防止把环境波动误判为算法回归；维护已知不稳定项及责任人。
- 质量门槛：按严重度设置阈值；先采集基线再定门槛；漂移告警与硬失败分开；阈值变更留审计记录。
- 安全与数据：凭证最小权限、日志脱敏、语音授权、留存期限、测试车辆隔离和制品完整性。

### 通过标准

每次构建自动执行一个短冒烟套件并发布可追踪报告；失败能保留完整工件，基础设施问题不会被计成模型质量回归。

**本阶段学习卡片**

- **先修：**Git 分支/PR、测试分层、版本化输入和资源管理。
- **重难点：**真实 HIL 设备需要独占调度、最小权限、失败收尾和工件保留；基线和质量门槛需要先测出环境噪声。
- **学习文档：**[CI 与质量趋势](/ci-quality)、[GitHub Actions 官方文档](https://docs.github.com/actions)。
- **B 站学习入口：**[GitHub Actions CI HIL 自动化回归](https://search.bilibili.com/all?keyword=GitHub%20Actions%20CI%20HIL%E8%87%AA%E5%8A%A8%E5%8C%96%E5%9B%9E%E5%BD%92)。

## 阶段 6：大模型辅助测试（第 18–20 周）

先理解传统质量链路，再让 LLM 协助文本工作。模型输出具有随机性、版本漂移和潜在隐私风险，因此要记录模型/提示版本、温度、输入摘要、输出和人工审核状态。

### 适合辅助的环节

- 从需求和设计文档生成候选意图、槽位边界、歧义表达和多轮路径草稿。
- 将历史失败日志摘要成待排查线索，或按可能组件进行聚类。
- 生成同义表达候选，经过语言质量、产品合法性和数据分布审查后进入语料。
- 以受限 JSON Schema 输出建议标签；由 schema 校验、规则断言和人工复核把关。
- 结合检索到的项目规范回答内部知识问题，答案必须带来源片段和版本。

### 不应交给自由生成结果单独决定的事情

- 是否执行有车辆安全影响的命令；是否通过关键业务验收；对 CAN 关键值是否满足精确阈值；未经审核地把客户音频发送到外部模型；自动改写基准标签或回归门槛。

### 通过标准

对模型辅助的收益和错误率分别测量；能复放同一请求；拒答/幻觉/格式错误有明确处理；确定性关键断言仍独立运行。

**本阶段学习卡片**

- **先修：**前五阶段的语料、评测、证据链和 CI 基础。
- **重难点：**结构化输出通过 schema 校验仍可能在语义上错误；LLM 裁判要用专家标注集校准；敏感语音/日志要受数据策略约束。
- **学习文档：**[大模型辅助测试](/llm-testing)、[OpenAI Evals 方法入口](https://platform.openai.com/docs/guides/evals)。
- **B 站学习入口：**[LLM Judge RAG 大模型评估测试用例生成](https://search.bilibili.com/all?keyword=LLM%20Judge%20RAG%E5%A4%A7%E6%A8%A1%E5%9E%8B%E8%AF%84%E4%BC%B0%E6%B5%8B%E8%AF%95%E7%94%A8%E4%BE%8B%E7%94%9F%E6%88%90)。

## 每周学习闭环

每周选一个可验证问题：写假设 → 定义数据和测量方法 → 运行实验 → 保存原始证据 → 写结论和局限 → 把稳定结论整理成知识页。每个结论注明“哪些条件下成立”，不要只记录命令或截图。

## 能力自测

- 我能否画出从麦克风输入到车辆状态变化的完整时序，并指出可观测边界？
- 我能否解释 WER/CER 的归一化规则、分母、错误分布及小样本限制？
- 我能否区分文件级音频回放、软件注入和真实声学注入覆盖的系统路径？
