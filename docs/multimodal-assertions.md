# 日志、UI 与多模态断言

多模态验证不是把越多工具堆在一起越好，而是针对每个需求选择互相独立、可信且能定位问题的观测面。

## 证据层级

| 证据 | 适合证明 | 局限 | 建议做法 |
|---|---|---|---|
| 结构化 ASR/NLU 事件 | 系统识别与语义输出 | 内部输出不等于业务完成 | 保存原始事件和 trace id |
| 业务 API/服务事件 | 执行请求被接收/处理 | 可能尚未改变实际状态 | 与状态回读交叉验证 |
| CAN/Ethernet 状态 | 车辆域状态变化 | 映射/周期/有效性配置错误会误导 | 使用正确 DBC/协议版本与有效位 |
| UI/可访问性树 | 面向用户的应用状态 | UI 可能滞后或只显示缓存值 | 检查语义节点与稳定窗口 |
| 截图/OCR | 最终视觉呈现和布局 | 动画、分辨率、字体、动态文案造成噪声 | 固定采集环境、裁剪区域、阈值与多帧确认 |
| TTS 音频/播报事件 | 系统给用户的反馈 | 说了成功不代表状态成功 | 可用作反馈断言，不作为唯一业务断言 |

**本知识点学习卡**

- **先修：**观测点、独立性和验证目标。
- **重难点：**日志、服务和 UI 可能来自同一缓存数据源，不一定是独立证据；说明证据之间的因果/独立关系。

## 事件与日志断言

优先根据事件 schema 断言字段，不要用宽泛正则搜索“成功”。事件至少应有组件、事件类型、会话/请求 id、单调或统一时钟时间、版本和必要字段。解析器需应对乱序、重复、缺失、截断和缓冲延迟。等待逻辑采用事件驱动或有上限轮询，超时后保存采集区间和最后状态。

**本知识点学习卡**

- **先修：**结构化日志、事件 schema 和异步等待。
- **重难点：**依赖易变文案会脆弱；处理乱序、重复、缓冲延迟，并保留原始日志与解析结果。

## UI 与 OCR

首先使用 accessibility tree、控件 id、应用测试接口或稳定的界面状态模型。如果必须 OCR：

- 固定屏幕分辨率、缩放、语言、亮度、主题和采集区域。
- 使用 ROI（感兴趣区域）而非整屏整图比较。
- 对动态时间、电量、动画、地图和光标做掩码。
- 记录 OCR 引擎/模型版本、识别置信度、检测框和原始截图。
- 用多帧持续满足条件，区分短暂过渡和稳定结果。
- 通过实际正负样本校准阈值，低置信度输出为“不确定”或人工复核，不得默认通过。

像素差分适合固定渲染回归，语义识别适合文字/状态验证；两者解决的问题不同。

**本知识点学习卡**

- **先修：**图像处理、ROI、置信度和控件树。
- **重难点：**优先语义控件状态；OCR 需要多帧稳定确认、动态区域掩码和低置信度人工复核。

## CAN/Ethernet 断言策略

状态可能以周期帧上报，先定义采样窗口和稳定条件。例如“目标值在 2 秒内出现，后续 500 毫秒连续有效且没有反向状态”。还要处理初始值恰好等于目标、帧丢失、信号超时、无效位、同名信号来自错误 ECU 等情况。确认信号值与单位的解码来自正确数据库版本。

**本知识点学习卡**

- **先修：**信号周期、有效性、服务生命周期。
- **重难点：**初值恰好等于目标、无效位或错误 ECU 都可能导致假通过；定义更新窗口、稳定时间和数据源版本。

## 一致性和独立性

对关键业务动作，建议形成三层因果链：

```text
识别/语义事件 → 服务/业务执行事件 → 独立状态观测（车辆信号或状态接口）
                                       ↘ 用户可见反馈（UI/TTS）
```

业务 API 和日志若共享同一错误数据源，不是真正独立的交叉证明。报告应说明观察面的独立程度和盲区。断言有冲突时保留所有证据并判为冲突/待诊断，而不是挑选看起来正确的一份。

**本知识点学习卡**

- **先修：**因果链、多重观测与冲突处理。
- **重难点：**同一业务链上的重复日志不构成独立验证；证据冲突应输出冲突状态并保留全部材料。

## 失败分类

推荐使用稳定枚举：`WAKE_MISS`、`ASR_MISMATCH`、`NLU_MISMATCH`、`DIALOG_STATE`、`BUSINESS_NOT_EXECUTED`、`VEHICLE_STATE_MISMATCH`、`HMI_MISMATCH`、`LATENCY`、`EVIDENCE_MISSING`、`INFRA_FAILURE`、`DATA_INVALID`、`INCONCLUSIVE`。一次用例可有一个主要失败和多个证据标签；不要将基础设施失败从报表中无声丢弃。

**本知识点学习卡**

- **先修：**错误模型、分类边界和不确定状态。
- **重难点：**测试结果不能只有 pass/fail；区分产品、环境、数据、证据和判定器故障，并避免静默忽略。
