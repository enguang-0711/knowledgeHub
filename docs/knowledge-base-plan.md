# 知识库分阶段建设方案

目标是逐步形成一份可检索、可验证、可运行、可维护的工程知识库，而不是一次性堆出很多长文。知识库内容按学习者的先修关系组织；每阶段都带有实际产物和验收条件。

## 读者与边界

### 目标读者

- 测试工程师：掌握语音测试基本概念，准备建设脚本和评测集。
- 自动化测试开发：熟悉 Python/CI，希望扩展到音频、车机、总线和 HIL。
- 语音算法/系统测试：需要统一 ASR、NLU、对话和业务结果的指标口径。
- 技术负责人：需要规划试点、设备投入、测试分层和质量门槛。

### 本库包含

概念解释、指标定义、工具使用、实验方法、参考架构、可复用代码/数据模板、项目复盘、来源与版本记录。

### 本库不替代

车厂/供应商项目规范、法规和功能安全分析、工具厂商手册、付费标准全文、车辆安全操作授权、针对量产系统的安全评估。项目具体接口、阈值和动作前置条件以适用的正式文件为准。

## 信息架构

```text
首页与路线
├── 00 系统视角：架构、边界、风险与测试策略
├── 01 测量基础：WER/CER、分类指标、时延、统计与实验设计
├── 02 音频基础：格式、声学链路、噪声、校准与注入
├── 03 语料资产：文本、TTS/真人语音、元数据、版本与许可
├── 04 算法评测：唤醒、ASR、NLU、对话状态、TTS
├── 05 车端集成：ADB、日志、HMI、CAN/Ethernet、HIL
├── 06 自动化工程：Python、pytest、Robot Framework、适配器与报告
├── 07 工程化：CI、基线、趋势、资源调度和数据治理
├── 08 AI 辅助：生成、检索、分类、裁判评估与风险控制
├── 09 实战项目：离线评测 → 台架闭环 → HIL/CI
└── 附录：术语、标准、工具矩阵、检查清单与模板
```

## 建设阶段和发布门槛

| 阶段 | 内容目标 | 可验收产物 | 发布门槛 |
|---|---|---|---|
| A. 可浏览 MVP（1–2 周） | 学习路线、架构、指标、知识贡献规范 | Pages 可访问；导航清楚；6 篇核心页 | 干净环境构建通过；所有内部链接有效；首页能引导新读者 |
| B. 离线语音评测（2–4 周） | 音频、语料、TTS、ASR/NLU 指标 | 样例语料清单、评估脚本、样例报告 | 能从清单复现评测；记录归一化和版本 |
| C. 设备闭环（3–6 周） | 注入、ADB、日志/UI、业务 API | 一套带适配器接口的端到端示例 | 台架前置条件、安全边界和失败分类明确 |
| D. 总线/HIL（依项目条件） | CAN/Ethernet、同步、设备资源治理 | 信号断言示例、HIL 检查清单 | 不依赖单一隐式环境；有仿真/回放替代路径 |
| E. CI 与趋势（2–4 周） | 流水线、工件、基线、回归看板 | 可复用 workflow、报告 schema | PR 构建可验证；主分支部署可追踪和回滚 |
| F. AI 增强与治理（持续） | LLM 生成/归因/知识检索 | 受控提示模板、评测集、审核规则 | 与确定性结果分开呈现；版本、输入来源、错误处理可审计 |

工期是个人/小团队的估算范围，不是承诺；可并行写作，但阶段验收门槛不应省略。

## 每篇知识页的标准结构

1. **摘要与适用读者**：一两句话说明解决什么问题。
2. **学习目标与先修知识**：能做什么，读之前需要知道什么。
3. **概念与边界**：名词定义、输入/输出、上游/下游。
4. **实现步骤**：工具、命令、配置、参数和版本。
5. **验证方法**：预期结果、反例、故障注入、验收口径。
6. **常见误区**：可能造成假阳性/假阴性的条件。
7. **项目练习**：小任务及可检查产物。
8. **参考来源**：官方文档/标准/论文/实测记录，带版本和访问日期。
9. **维护信息**：负责人、最近验证日期、适用项目/版本、待确认项。

## 知识质量和来源分级

- **S1 标准/官方定义**：标准组织、协议或工具官方文档。引用编号、标题、版本和具体章节；标准全文可能受版权限制，只提供合法的目录/摘要引用。
- **S2 可复现实测**：有环境、输入数据、软件版本、步骤、原始结果和重复次数的实验。
- **S3 项目经验**：明确标注项目、平台、时间、样本范围和不可泛化条件；需先脱敏并确认发布权限。
- **S4 建议/假设**：标注为建议，提供验证办法，不写成事实结论。

对数字、门槛和“行业主流”“效率提升”等说法必须给出处或实验依据。对易变页面记录访问日期；对工具命令记录验证的版本。

## 仓库与页面维护流程

1. 新内容先用 `docs/templates.md` 的模板创建草稿，给出目标读者、来源、验证日期和状态。
2. 一个页面聚焦一个主题；跨主题只链接，避免复制产生多个事实版本。
3. 页面提交通过 GitHub Pull Request；检查 Markdown 链接、拼写、构建和代码示例。
4. 涉及车端命令、危险动作或外部模型上传数据的页面，需要额外安全/隐私复核。
5. 评审通过后合并到 `main`，Actions 自动构建并部署 Pages。
6. 每季度复查“待确认”和已过验证期页面；工具/接口升级时更新版本和回归记录。

## GitHub Pages 配置说明

仓库根目录工作流 `.github/workflows/pages.yml` 在推送 `main` 后构建并部署，也会在 Pull Request 上只执行构建。首次启用时，到仓库 Settings → Pages 将 Source 设置成 **GitHub Actions**。项目站点的 base path 按仓库名自动设置；`username.github.io` 仓库或绑定自定义域名时将 `VITEPRESS_BASE` 设为 `/`。

## 近期执行清单

### 第一周：发布 MVP

- 推送仓库并启用 Pages；确认 Actions 权限、基础路径和搜索。
- 邀请 1–2 位目标读者按首页路线阅读，记录断链术语和跳步。
- 复核架构、指标和路线三页的术语口径。

### 第二至四周：补齐可运行例子

- 增加音频文件元数据检查和 CER/WER 小型评测脚本。
- 选取有发布权限的虚构或开源小语料，发布 manifest，不直接放客户录音。
- 固定 Python 依赖、样例输入、预期输出和 CI 验收。

### 第二个月：设备闭环

- 先设计接口和故障分类；对没有实验硬件的读者提供 simulator/mock。
- 逐项补充 ADB、播放器、记录器、日志和总线适配器的安装/恢复方法。
- 发布一条短冒烟用例的完整执行证据和已知限制。

### 第三个月及以后：治理和 AI 辅助

- 建立内容过期提醒和来源复核节奏。
- 发布 AI 辅助功能的离线对照实验；明确人工审核时间和错误成本。
- 只在收益被测量、隐私边界合格后把 AI 步骤放进正式流水线。
