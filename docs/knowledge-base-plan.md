# 软件测试与质量工程知识库建设方案

本库的总定位是**软件测试与质量工程学习知识库**。内容组织以跨行业的方法和工程能力为主干，再按系统类型、行业或工作场景建设专题。当前车载语音自动化测试是最完整的应用专题之一；后续主题应复用同一套内容结构、证据要求和学习卡标准。

建设重点不是一次性扩充目录，而是让每个已发布主题都能回答：学什么、先学什么、难在哪里、怎样动手验证、结论依据是什么。

## 读者与内容边界

### 目标读者

- 软件测试工程师：希望系统学习测试设计、风险分析和质量度量。
- 测试开发工程师：希望用 Python、自动化框架和 CI 建立可维护的执行体系。
- AI/数据系统测试人员：希望评估模型行为、数据和应用链路。
- 行业系统测试人员：希望把通用测试工程方法应用到汽车、语音、移动端或其他复杂设备系统。
- 技术负责人：希望规划测试分层、质量门槛、资源投入和知识治理。

### 本库包含

测试基础、测试开发、自动化架构、数据与指标、证据与可观测性、CI 和质量治理、AI 应用测试，以及有清晰边界的行业专题、项目练习、模板和参考资料。

### 本库不替代

产品需求和项目规范、法规与安全分析、厂商手册、标准全文、客户合同要求、工具访问授权或正式的生产系统安全评估。具体接口、法规解释、车辆动作和数据使用以项目适用的正式文件与授权为准。

## 信息架构

```text
知识库首页与路线
├── 通用测试主干
│   ├── 需求分析、风险和测试设计
│   ├── 测试开发：Python、pytest、Robot Framework
│   ├── 质量度量、统计和实验设计
│   ├── 可观测性、证据管理和失败分类
│   └── CI、报告、回归和质量治理
├── AI 与智能系统测试
│   ├── 传统软件与模型系统的测试边界
│   ├── 评测集、LLM Judge、RAG 和鲁棒性
│   └── 数据安全、隐私和模型版本治理
├── 行业/系统专题
│   ├── 车载语音自动化测试（当前已展开）
│   ├── API/服务、Web/移动、性能/可靠性等（逐步建设）
│   └── 每个专题连接回通用主干，不重复定义基础方法
└── 知识资产
    ├── 术语词典、工具与来源
    ├── 可复用模板与检查清单
    └── 实战项目、维护流程和 GitHub Pages
```

站点导航会明确区分“通用能力”和“领域专题”。规划中的方向必须标为规划中，不能因为出现在目录里就暗示已有完整教学内容。

## 分阶段建设与验收门槛

| 阶段 | 建设目标 | 代表产物 | 发布门槛 |
|---|---|---|---|
| A. 通用学习骨架 | 首页、知识地图、通用路线、导航与页面规范 | 可理解的内容地图和学习起点 | 新读者能区分通用内容、专题内容和规划内容 |
| B. 测试工程基础 | 需求/风险/用例、Python 自动化、指标、证据 | 可本地运行的练习项目和报告 | 干净环境可复现，失败能定位，指标定义完整 |
| C. AI 应用测试 | 评测数据、基线、模型比较、RAG/裁判方法 | 可复放的 AI 评测样例 | 提示、模型、数据版本清楚；不以模型自评充当事实 |
| D. 领域专题 | 选择真实学习需求较高的系统，补齐架构、工具和边界 | 专题导览、专项路线、模块文章和实战 | 通用基础与领域特有知识区分清楚；安全/授权边界明确 |
| E. CI 与持续治理 | 质量趋势、来源复核、链接与构建校验 | 工作流、内容维护清单 | PR 构建通过，变更可追溯、站点可回滚 |
| F. 扩展专题 | 按需求增加 API、Web/移动、可靠性等方向 | 具有独立验收任务的专题 | 先补完整内容再公开标记为已建设 |

工期由贡献人数、设备、资料许可和验证条件决定。先做可复现的代表性样例，再扩展主题深度；不以文章数量作为质量指标。

## 每篇知识页的标准结构

1. **摘要与目标读者**：说明本页解决的问题及适用边界。
2. **学习目标与先修知识**：读完能做什么、需要先会什么。
3. **概念与边界**：术语、输入/输出、依赖关系；必要时区分通用和行业定义。
4. **分步解释与实现**：参数、时序、公式、代码、工具和版本。
5. **验证方法**：正反例、故障情景、预期证据和验收条件。
6. **重难点与常见误区**：易混概念、隐藏假设、测量和调试难处。
7. **项目练习**：可在本机、mock 或获授权的设备上完成的任务。
8. **学习资源**：优先官方资料，再提供论文/教程和 B 站搜索入口；具体视频需人工核实后才作为推荐。
9. **来源与维护**：版本、发布日期/访问日期、适用范围、验证状态和待确认项。

### 每个主要知识点的学习卡字段

- **专有名词：**英文全称、中文译名、缩写和常见别名。
- **一句话定义：**初学者能够复述的短解释。
- **掰开说明：**讲清输入、过程、输出、上下游关系，并通过例子/公式/时序逐步解释。
- **目标系统中的用途：**说明它解决什么问题，以及在当前主题/行业如何验证。
- **重难点：**至少包含先修、易混概念、常见误区和一个调试/评估难点。
- **学习入口：**文档、官方资料、针对该知识点的 B 站搜索或经核验的视频。
- **动手验收：**一个可观察的练习或自测题。

B 站搜索结果只是发现课程的入口，不代表本站已经审阅或背书具体视频。标准、接口和产品行为要以适用版本的正式文档为依据。

## 来源与质量标记

- **官方/标准定义：**记录组织、文件编号、版本和章节；注意版权。
- **可复现实测：**记录系统、输入数据、软件/模型版本、步骤、原始结果和重复次数。
- **项目经验：**说明行业、项目范围、时间与不可泛化条件，发布前完成脱敏和授权核对。
- **建议/假设：**显式标注，给出适用条件及如何验证。

数字、门槛、行业趋势或收益结论需要来源或实验依据。工具命令要尽量记录验证版本；易变网页保留访问日期。

## 内容维护与发布

1. 新页面说明主题归属：通用主干、AI 测试或某个领域专题。
2. 复用统一模板，交叉主题用链接引用，避免事实复制后产生版本冲突。
3. 提交前检查术语、内部链接、代码示例、来源和构建结果。
4. 涉及设备控制、敏感数据、外部 AI 服务或个人语音时，增加相应的安全、授权与隐私说明。
5. 通过 GitHub Actions 构建并部署 Pages；失败时修复或回滚到已知可用版本。
6. 定期清理失效链接，复核过期内容、工具版本和规划项状态。

## GitHub Pages 与站点组件

项目使用 VitePress，工作流 `.github/workflows/pages.yml` 根据仓库名配置项目站点路径并构建部署。首次发布需要在仓库 Settings → Pages 选择 GitHub Actions；自定义域名或用户站点可将 base 设置为 `/`。

知识页右侧目录上方保留主题视频学习区。组件根据当前知识页提供对应 B 站搜索词；读者可粘贴视频 BV 号或链接在页内播放。窄屏时播放区转到正文下方，最近播放记录只保存在本地浏览器。

## 当前优先顺序

1. 让首页、知识地图和通用路线准确表达“测试与质量工程主库、车载语音是行业专题”。
2. 补齐通用测试设计、API/mock 示例和通用指标案例，降低入门对汽车领域的依赖。
3. 为 AI 测试、CI 和证据管理补充从空目录可执行的示例项目。
4. 维护车载语音专题中的来源、版本、边界与 B 站学习入口。
5. 根据实际学习需求选择下一个专题，并在内容达到发布门槛后加入导航。
