# 车机、总线与 HIL 集成

本页提供通用工程学习框架。实际设备命令、DBC、诊断步骤和控制权限由项目授权规范决定；不要在道路行驶中运行自动化控制脚本。

## Android/车机基础

从只读和低风险操作开始：列出设备、确认序列号、读取系统/应用版本、抓取日志、检查进程与崩溃信息。ADB 自动化应具备设备唯一选择、连接健康检查、命令超时、退出码检查、输出归档和异常断连处理。

常见运维流程包含安装/升级、重启、清除应用状态和刷写。它们会改变被测环境，应使用显式维护步骤、镜像校验、操作人和恢复方案；不可将“清理环境”隐藏在每条用例的前置 fixture 中。

日志采集建议使用过滤表达式、时间区间和组件标识；保留原始 logcat，再产出解析事件。解析器对系统版本变化要有兼容策略；若可能使用结构化日志或诊断接口，比依赖自然语言日志稳定。

**本知识点学习卡**

- **先修：**ADB、设备状态、日志和版本管理。
- **重难点：**多设备要按序列号选择；刷机和清数据需显式维护流程，设备离线与产品失败要区别处理。

## CAN 信号测试

基本对象：物理总线帧、仲裁 ID、DLC、数据字节、周期、节点、信号位布局、缩放/偏移、单位、枚举、有效位和超时策略。DBC 描述需与 ECU 软件/车型配置版本一致。

将“空调打开”断言转成明确的信号契约：信号名、目标值及单位、有效位要求、允许的更新窗口、连续稳定样本数、超时、总线通道和观测方向。对于复合状态，要检查相关信号一致性；只读回发命令帧并不能证明 ECU 已执行。

测试适配器优先区分 `subscribe/read` 与 `send/write`。写总线动作必须明确授权、台架隔离、允许 ID/信号和安全联锁；一般语音功能回归应优先消费信号或使用仿真输入，避免无约束发送。

**本知识点学习卡**

- **先修：**CAN 帧、DBC 解码、周期和有效位。
- **重难点：**命令帧不是执行证明；校验状态反馈、信号有效位、稳定窗口和 DBC/车型版本。

## Ethernet 与服务接口

了解项目用到的网络拓扑、VLAN、服务发现、订阅生命周期、事件/方法语义、超时与重试、诊断通道和流量抓取。SOME/IP、DoIP 等协议细节需要结合 ECU 配置和正式工具文档学习。断言需检查服务实例、版本、返回码、业务事件以及最终状态，而不只是“端口可连”。

**本知识点学习卡**

- **先修：**网络拓扑、服务发现、事件和超时。
- **重难点：**网络可达不等于服务实例/版本正确；按项目协议核查发现、订阅、返回码和最终车辆状态。

## HIL 资源与状态恢复

执行前校验台架身份、设备版本、通道映射、校准有效期、仿真模型、车辆状态和急停链路；执行中记录资源锁、软件版本、环境参数和同步时钟；执行后恢复基线、检查残留会话并释放资源。恢复不成功应将环境标记为不可用，不能继续跑后续用例。

**本知识点学习卡**

- **先修：**实时仿真、接口映射和安全联锁。
- **重难点：**模型和通道映射会影响真实性；健康检查、资源独占、急停和恢复失败必须纳入执行判定。

## 同步和证据关联

证据可能来自 Android 单调时钟、总线分析仪、音频采集机和 CI runner。记录各时钟源、同步协议、时间偏移与误差；使用 run/session/trace id 关联日志。若不能进行时钟同步，至少以明确的播放标记/硬件触发信号建立时间关系，并扩大时延不确定区间。

**本知识点学习卡**

- **先修：**时钟源、同步和 trace ID。
- **重难点：**跨机器时间戳不能默认可比较；明确同步误差，必要时用硬件标记建立因果关系。

## 多屏一致性

多屏验证先定义主从关系、状态传播延迟、驾驶员/副驾/后排权限和用户切换策略。检查目标屏控件可见/可操作、其他屏显示同步以及权限冲突后的预期表现。OCR 只作为视觉证据之一；应用状态、可访问性节点或总线状态通常更稳定。

**本知识点学习卡**

- **先修：**分布式状态同步、权限和最终一致性。
- **重难点：**屏幕短暂延迟与永久不一致需要不同判据；定义同步期限、目标屏和多用户/音区权限。
