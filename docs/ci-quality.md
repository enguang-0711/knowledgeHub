# CI、报告与质量趋势

流水线的目标是让可比较的测试在正确环境中重复执行，并保留足够证据定位变化。自动触发本身不等于自动化质量。

## 测试金字塔与触发策略

| 层 | 典型检查 | 运行位置/频率 |
|---|---|---|
| 静态与单元 | Python lint/type、schema、解析器、指标计算 | 每个 PR，快且稳定 |
| 离线算法 | 冻结音频的 ASR/NLU 评估 | 每个模型候选或每日；按样本量控制耗时 |
| 模拟集成 | 会话流程、业务 mock、失败/重试路径 | 每个 PR 或主干 |
| 设备冒烟 | 少量关键用例、设备健康检查、真实音频链路 | 合并后或候选版本 |
| HIL 回归/长稳 | 多噪声、多音区、多轮、压力与恢复 | 夜间、发布候选或受控排程 |

## 每次运行的最小元数据

仓库 commit、应用/固件/模型/配置版本、语料与 noise set 版本、执行器版本、设备/台架 ID、校准状态、运行时间和时区、触发原因、环境状态、各阶段结果、原始证据索引、失败分类、判定器版本。

## 失败策略

- **重试**：只对已知瞬时基础设施故障，记录每次尝试和最终状态；产品失败不应靠重试变绿。
- **超时**：按阶段设置超时；超时产生 `TIMEOUT` 证据并保存最后事件，不要统一延长等待掩盖性能退化。
- **隔离**：不稳定用例有责任人、复现率、到期日期和修复计划；隔离项仍出现在报告。
- **取消**：避免多个 job 同时控制同一台车机/总线；对硬件资源加锁并在取消时安全收尾。
- **工件**：保存日志、识别事件、总线 trace、截图、回采音频和测试清单；设置访问控制与保留周期。

## 趋势治理

趋势图应同时展示总体与场景分层的指标、分母、运行版本、环境和测试数据版本。用冻结基准评估模型变化，定期检查测量设备和台架重复性。将阈值设为“质量门槛”，但另设“告警观察区间”；当误差源于环境变化时先调查台架。阈值变更要记录理由、审批、影响范围和生效时间。

## GitHub Actions 与 HIL 的边界

Pages 工作流只负责构建和发布知识站点。本仓库不含车辆接口，因此不应把真实车控/HIL 执行塞入公开知识库站点的 CI。将来加入测试代码时，离线脚本可在 GitHub-hosted runner 运行；真实设备 job 应放在受控 self-hosted runner，采用最小权限、网络隔离、设备锁、手动审批/策略和安全联锁。

## 报告建议结构

1. 摘要：通过/失败/基础设施失败/数据无效/未判定数量。
2. 版本与环境：SUT、模型、语料、设备、校准和 CI 信息。
3. 指标：定义、值、分母、历史基线和分层结果。
4. 用例明细：阶段、失败类型、预期/实际、安全严重度。
5. 证据：结构化事件和原始工件链接。
6. 归因状态：已确认根因、假设、责任人、相关缺陷与复测。

自动生成报告要能从汇总数字钻取到单条用例及输入资产；只发布红绿灯不足以支持工程决策。
