# 车载视觉 ECU 性能、回归与 CI

视觉模型在开发机上达到高精度，不代表它能在目标 ECU 上按时、稳定地运行。端侧验证必须把模型推理、输入预处理、数据搬运、后处理、多相机并发、温度和整车软件调度一起纳入测量，并保留可追溯的构建与数据版本。

## 术语拆解

- **ECU（Electronic Control Unit）**：车载电子控制单元。计算平台、加速器、内存、操作系统和软件栈因项目而异。
- **SIL/HIL**：软件在环/硬件在环；边界和用法见[仿真与回放专题](/vehicle-vision/testing/simulation-replay)。
- **端到端时延**：明确起点和终点的完成时间。可以是传感器帧到感知消息，也可以是输入到 HMI；报告必须给出边界。
- **p50/p95/p99**：时延分布分位数。p99 表示 99% 观测值不超过该值，仍需说明样本量、预热和异常值处理。
- **热降频/thermal throttling**：温度或功耗管理降低频率，可能造成长时间运行的帧率和时延退化。
- **CI 门禁**：流水线对质量条件作出的 pass/fail/needs-review 决策。阈值来源需与项目要求和基线绑定。

## 一、性能预算与测量边界

先从产品需求或实时调度设计获得预算，拆分到相机采集/解码、预处理、内存传输、推理、后处理、跟踪/融合、发布和 HMI。串行阶段可累加，异步/并行阶段不能简单相加；应以共同时间基准直接测端到端，并用阶段时间诊断瓶颈。

至少报告：输入/完成帧数、实际帧率、丢帧/超时、端到端与阶段延迟的 p50/p95/p99/最大值、启动和稳定时间、CPU/GPU/NPU 利用率、内存/显存峰值、温度/功耗（若可用）、异常重启和长时间趋势。测量包含目标分辨率、相机路数、并发负载、模型/量化版本、固件/驱动、编译器、环境温度、预热、计时工具和时钟域。

平均 FPS 不能说明单帧最坏时延；模型 benchmark 也可能不含解码、预处理和队列。若输入速率高于处理能力，队列增长会让“帧率看起来稳定”但结果越来越过期，因此记录输入帧 ID 到输出帧 ID 的延迟和 backlog。

## 二、分层性能测试

1. **模型算子基准**：定位算子与精度/量化影响，作为诊断数据，不等于 ECU 端到端结果。
2. **目标 ECU 冒烟**：确认镜像/模型可加载、输入输出协议正确，检查首帧和初始化开销。
3. **持续稳定性**：目标分辨率和多路并发下运行足够时长，观察热状态、内存增长、帧率波动、日志错误和重启。
4. **负载与干扰**：按产品环境叠加其他 ECU/进程负载、通信和存储活动，测尾延迟及降级行为。
5. **资源/异常边界**：检查内存不足、相机掉线、输入突发、过热/保护状态和恢复路径；按安全流程在受控台架执行。

显卡/ECU 温度、频率和功耗若拿不到硬件 telemetry，应明确记录“未测”，不要用主机指标代替。

## 三、精度与性能联合回归

将每个结果绑定代码 commit、模型权重 hash、标定/预处理版本、数据集/标注版本、评估脚本、固件、驱动、编译选项、硬件 ID 和随机种子。成对比较新旧版本：同一冻结集、同一配置，分别看总体和安全关键切片的质量变化、时延分位数、资源峰值及失败样本。

门禁分层更可靠：PR 快速集检查格式、接口、少量冻结样本和启动；每日回归跑较完整的离线/仿真集；目标硬件和 HIL 回归按资源安排执行；发布候选再做长时/目标场景验证。哪些门禁是硬失败、哪些需要人工复核，由需求风险和团队流程决定，不以通用示例数值设产品阈值。

## 四、CI 流水线产物

建议流水线步骤：校验数据/模型许可证与 hash → 构建软件/模型包 → 部署到模拟器或授权设备 → 运行固定输入 → 收集结构化输出、日志和性能 telemetry → 算指标/按场景切片 → 对比基线 → 标记失败类型并归档报告。设备资源应由调度器锁定，测试结束后清理进程、恢复环境并记录刷写/部署版本。

机器可读报告可包含：

```json
{
  "run_id": "vision-regression-...",
  "software_commit": "...",
  "model_sha256": "...",
  "dataset_version": "...",
  "calibration_id": "...",
  "hardware_profile": "...",
  "scenario_slices": [],
  "quality_metrics": {},
  "latency_ms": {"p50": null, "p95": null, "p99": null},
  "dropped_frames": 0,
  "artifacts": []
}
```

字段需与团队 schema 对齐；不应把 `null` 当作 0 或通过。报告需链接到失败帧/片段、预测与标注、日志和运行环境，而不是仅存总分。

## 五、趋势、波动与失败分类

趋势图同时画指标、样本数、切片分母、版本和硬件条件。出现退化先验证是否同一数据、同一标注、同一推理精度和设备状态；再分辨模型/预处理、编译、驱动、调度、温度、数据管线或评测器变化。小样本波动要展示区间和重复结果，避免仅凭一次 run 误判。

失败分类至少包括：构建/部署失败、接口/配置错误、数据损坏、功能失败、精度退化、性能超限、资源泄漏、超时/丢帧、环境/设备不可用、判定器异常。区分产品缺陷和基础设施失败，重试只能按规则处理，并保留首次失败证据。

## AI 时代的 CI 使用方式

LLM 可以归纳日志、聚类新增错误帧、对比缺陷报告和提出根因候选。摘要应带原始证据链接、置信/不确定提示和模型版本；确定性代码负责指标计算与门禁。不要把模型生成的“看起来与基线等价”直接作为放行结论，也要防止日志/图像提示注入污染模型分析。

## 常见重难点

- **开发机快、ECU 慢**：检查目标算子支持、数据格式转换、内存拷贝、线程数和真实并发路数。
- **平均 FPS 达标但功能延迟**：计算输入帧到最终消费端的年龄，检查排队与丢帧策略。
- **短测通过、长测退化**：比较热状态、频率、内存、句柄、缓存和周期性后台工作。
- **版本对比不可解释**：确认模型、数据、标注、标定、软件和设备是否全部固定。
- **CI 偶发红灯**：先看设备竞争、数据/网络和时钟同步；保留首次失败，分类后按政策重跑。

## 动手练习与验收

用目标 ECU 或明确标成模拟环境的设备，运行固定视频回归；记录输入帧 ID/时间戳、输出时间、资源数据和精度；执行冷启动、稳定运行和缺帧场景；生成机器可读报告与失败帧链接；构造一次精度退化和一次时延退化，验证流水线可分别识别。验收时可从一条 CI 结果追溯到 commit、模型、数据、硬件和具体失败样本。
