# 车载视觉需求工程

## 学习目标

把产品功能描述转成可实现的感知输出、运行约束和验收边界。视觉需求必须说明目标对象、输入相机、输出字段、坐标系、更新时间、有效区域、置信度语义及失效行为。

## 需求拆解

以“检测前方车辆并提供距离”为例，澄清类别定义、遮挡/截断规则、距离坐标系、有效距离范围、目标生命周期、输出频率、允许延迟、环境和 ODD（运行设计域）。若下游控制或告警依赖该输出，应说明失效时如何降级。

## 指标和约束

将精度指标映射到场景与标签协议，说明匹配规则、分层和统计方法。同步定义帧率、端到端时延、分辨率、算力、内存、功耗、启动时间和数据带宽预算。关键指标要有证据来源和责任接口。

## 常见遗漏

- 只写模型 mAP，不定义坐标、时戳、无效值与生命周期。
- 把开发数据上的指标当成完整 ODD 质量承诺。
- 未区分目标漏检、系统丢帧、摄像头遮挡和标定失效。
- 对域外场景没有安全降级或可观测状态。

## 练习与验收

选一个低速泊车或舱内提醒功能，写出输入输出契约、场景边界、资源预算和失败模式。让接口消费者能据此独立实现 mock 并判定有效/无效输出。

## 需求追踪与量化

把自然语言需求拆成输入条件、可观察输出、场景边界、时效预算、精度/误报代价、资源约束和失效行为。每项指标定义分子、分母、样本范围、统计窗口和运行版本；“实时”“稳定”“准确”必须转化成可测条件。

为每条需求建立“需求 ID → 设计模块 → 数据/标签 → 实现参数 → 测试用例 → 结果证据”的追踪关系。跨团队评审时记录未决项、假设、责任人和关闭标准；需求变更后评估接口、模型数据和回归资产的影响。

**验收产物：**用一个功能完成需求基线和追踪矩阵，并让测试工程师能仅凭文档构造正例、边界例和失效例。未定义的阈值标为待确认，不能悄悄写入算法常量。
