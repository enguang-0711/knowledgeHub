# 功能需求与视觉系统架构

视觉开发从功能契约开始，而不是先挑一个模型。算法必须在明确的输入、输出、场景、时效和失效处理条件下设计；否则离线精度再高，也可能无法接入车辆功能。

## 把产品需求变成算法契约

至少明确以下字段：

| 项目 | 需要约定的内容 |
|---|---|
| 输入 | 相机 ID、图像格式、分辨率、帧率、采集时间戳、标定和车辆状态版本 |
| 输出 | 类别/状态/几何定义、坐标系、单位、置信度含义、有效标志和输出频率 |
| 场景范围 | 目标类别、道路/座舱条件、昼夜和天气、适用边界及排除条件 |
| 实时约束 | 端到端时限、最大容许数据年龄、并发输入、内存和算力预算 |
| 失效行为 | 无效帧、断流、超时、标定无效或资源不足时的输出与恢复策略 |
| 下游用途 | 哪些功能消费输出、如何处理过期数据、是否需要置信度或不确定状态 |

“识别车辆”还需进一步定义车辆类别范围、遮挡/截断标签、框或轨迹坐标、最小目标尺度和评估边界。需求歧义会在训练标签、评估口径和下游接口中重复出现。

## 画出端到端数据链路

常见链路是：

```text
图像传感器 → 驱动/ISP → 解码或颜色转换 → 预处理 → 模型/几何算法
→ 后处理与时序逻辑 → 感知接口 → 融合/车辆功能 → HMI 或执行策略
```

为每段标注执行设备、数据格式、坐标系、时间戳来源、线程/队列、延迟和可观测日志。训练数据从哪个节点采集也要标明：若离线图片跳过 ISP、传输和同步，就无法覆盖这些节点的真实行为。

## 组件边界与设计取舍

将相机接入、预处理、推理、后处理、跟踪和功能逻辑定义为可独立验证的组件。接口说明输入输出所有权、错误码、资源生命周期和版本兼容性。模块越多不必然越好；拆分应让状态、性能瓶颈和故障原因容易观察。

架构方案要显式比较精度、端到端延迟、峰值内存、功耗、数据需求、平台兼容和维护成本。关键计算的并行化、量化或异步执行可能提高吞吐，也可能增加排队延迟或改变结果顺序。

## 常见问题

- 用 AP/mAP 代替功能需求，没有说明关键类别、场景或时效。
- 输出坐标、单位和置信度没有契约，集成方只能猜测。
- 只画模型结构图，遗漏相机、ISP、预处理、后处理和下游使用方。
- 发生故障时复用上一帧结果，却没有数据年龄或过期状态。

## 练习与完成标准

选择一个具体功能，交付一页需求契约和一张数据链路图；再设计“相机断流、图像格式错误、推理超时”三个异常状态。另一位开发者应能据此说明算法边界、接口行为和需要采集的证据。
