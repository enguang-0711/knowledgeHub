# C++、CMake 与资源管理

车端视觉常要在 C++ 中运行推理、图像变换和时序逻辑。重点不是背语法，而是能安全管理大块图像内存、并发状态和平台依赖，并让工程可重复构建。

## 必备语言知识

- **对象生命周期与 RAII：**让对象构造/析构控制锁、缓冲区、文件和推理上下文的释放。避免手工 `new/delete` 与跨分支释放。
- **值、引用和移动：**理解什么时候复制图像/张量，什么时候传递只读引用或转移所有权。接口应明确对象是否仍由调用者持有。
- **智能指针：**用 `unique_ptr` 表达唯一所有权；只有确有共享生命周期时才使用 `shared_ptr`。循环引用可用弱引用处理。
- **容器和内存：**理解 `vector` 扩容、容量、连续布局和迭代器失效。图像数据可能很大，隐式复制会造成延迟和内存峰值。
- **异常与错误码：**库边界要定义错误传播方式；实时路径不能让未处理异常越过线程或进程边界。
- **并发：**掌握线程、互斥锁、条件变量、原子量和生产者/消费者模型。锁的保护范围要小，避免持锁执行耗时推理。

## 图像缓冲区的所有权

许多图像对象采用共享底层存储或外部内存视图。复制一个头部对象可能只是增加引用计数，也可能复制全部像素，必须查清所用库的语义。以下问题应写进接口契约：

1. 缓冲区由谁分配和释放？
2. 被异步任务持有期间，源内存是否仍有效？
3. 调用方能否在处理期间修改或重用缓冲区？
4. 行跨度、对齐和通道布局是否与假设一致？

## CMake 工程组织

按 target 声明源文件、头文件、链接库、编译特性和依赖，尽量减少全局编译选项。区分 Debug 与 Release 配置；将可执行程序、库和测试组织成独立 target。依赖库版本、编译器、架构和工具链应可记录，交叉编译时尤其要区分主机工具和目标库。

建议工程提供一条干净构建路径：安装依赖、配置 build 目录、编译、运行样例和检查退出码。构建说明应包含实际命令与已验证的平台。

## 调试与质量工具

使用编译警告和 AddressSanitizer 等工具发现越界、释放后使用和泄漏；用调试器检查崩溃栈和线程状态；对疑似热点使用 profiler 验证。工具只能缩小问题范围，结论仍需对应到输入、调用路径和资源生命周期。

## 常见问题

- `shared_ptr` 被当作默认所有权模型，导致资源释放时机不可控。
- 异步推理引用调用方缓冲区，任务运行时内存已被重用。
- 队列无上限，消费速度跟不上相机输入后内存持续增长。
- 只在开发机 Debug 构建通过，没有验证目标架构和 Release 配置。

## 练习与完成标准

实现一个 C++ 视频处理程序，提供明确的帧对象所有权、有限长度队列、超时和错误日志；通过 CMake 在干净目录构建。用测试或调试工具验证停止/异常路径会回收线程和缓冲区。
